# Chepter2. 리팩터링 원칙

## 1. 리펙터링 정의
1. 코드베이스를 정리하거나 구조를 바꾸는 모든 작업을 재구성(restructuring)이라는 포괄적인 용어로 표현하고, 리팩터링으 재구성 중 특수한 한 형태로 본다.
2. 리펙터링하기 전과 후의 코드가 똑같이 동작해야 한다. 
3. 리팩터링과 성능 최적화는 목적이 다르지만, 변경을 할때 프로그램의 전반적인 기능은 그대로 유지한다.

## 2. 두개의 모자
소프트웨어를 개발할 때 `기능 추가`와 `리팩터링`이라는 두 가지 모자가 있다. 기능을 추가 할 때는 기존 코드를 절대 건드리지 않고 새 기능을 추가해야 한다.
반면 리팩터링할 때는 기능 추가는 절대 하지 않기로 다짐한 뒤 오로지 코드 재구성에만 전념한다.

## 3. 리팩터링 하는 이유
1. 리팩터링하면 소프트웨어 설계가 좋아진다.
2. 리팩터링하면 소프트웨어를 이해하기 쉬워진다.
3. 리팩터링하면 버그를 쉽게 찾을 수 있다.
4. 리팩터링하면 프로그래밍 속도를 높일 수 있다.

## 4. 언제 리팩터링해야 할까?
1. 3의 법칙
   1. 처음에는 그냥 한다.
   2. 비슷한 일을 두 번째로 하게 되면, 일단 계속 진행한다.
   3. 비슷한 일을 세 번째 하게 되면 리팩터링한다.
2. 준비를 위한 리팩터링: 기능을 쉽게 추가하게 만들기
   1. 리팩터링하기 가장 좋은 시점은 코드베이스에 기능을 새로 추가하기 직전이다.
3. 이해를 위한 리팩터링: 코드를 이해하기 쉽게 만들기
   1. 이해를 위해 리팩터링 하는 행동은 코드를 이해하는데 도움이 된다.
4. 쓰레기 줍기 리팩터링
   1. 원래 하려던 작업과 관련 없는 일을 발견했을때, 간단히 수정할 수 있는 것은 즉시 고치고, 시간이 좀 거리는 일은 짧은 메모를 남긴 뒤에, 하던 일을 끝내고 나서 처리한다.
5. 계획된 리팩터링과 수시로 하는 리팩터링
   1. 보기 싫은 코드를 발견하면 리팩터링하자. 그런데 잘 작성된 코드 역시 수많은 리팩터링을 거쳐야 한다.
   2. 새 기능을 추가하기 쉽도록 코드를 수정하는 것이 기능을 가장 빠르게 추가하는 길이다.(수시로 하는 리팩터링)
6. 오래 걸리는 리팩터링
   1. 리팩터링에 리소스를 소비하지말고, 시간이 날 때마다 조금씩 개선해 나가자.
7. 코드 리뷰에 리팩터링 활용하기
   1. 코드 리뷰는 개발팀 전체에 지식을 전파하는 데 좋다.
   2. 코드 리뷰를 하면 다른 사람의 아이디어를 얻을 수 있다는 장점도 있다.
   3. 리팩터링은 코드 리뷰의 결과를 더 구체적으로 도출하는 데에도 도움된다.
   4. 가장 좋은 리팩터링 리뷰 방법은 짝 프로그래밍이다.
8. 관리자에게는 뭐라고 말해야 할까?
   1. 관리자가 기술에 정통하고 설계 지구력 가설도 잘 이해하고 있다면 리팩터링의 필요성을 쉽게 설득할 수 있다.
   2. 하지만, 기술을 모르는 상당수의 관리자와 고객에게는 리팩터링한다고 말하지 말아야 한다.
9. 리팩터링하지 말아야 할 때
   1. 지저분한 코드를 발견해도 굳이 수정할 필요가 없다면 리팩터링하지 않는다.
   2. 리팩터링하는 것보다 처음부터 새로 작성하는 게 쉬울 때도 리팩터링 하지 않는다.

## 5. 리팩터링 시 고려할 문제
1. 새 기능 개발 속도 저하
   1. 리팩터링을 자주하여 코드 베이스를 건강하게 만든다. 건강한 코드베이스는 기존 코드를 새로운 방식으로 조합하기 쉬워서 복잡한 새 기능을 더 빨리 추가할 수 있다.
   2. 리팩터링은 오로지 경제적인 이유로 해야 한다.
2. 코드 소유권
   1. 코드 소유권이 나뉘어 있으면 리팩터링에 방해가 된다.
   2. 코드의 소유권을 팀에 두어서 느슨하게 한다.
3. 브랜치
   1. 현재 흔히 볼 수 있는 팀 단위 작업 방식은 버전 관리 시스템을 사용하여 팀원마다 코드베이스의 브랜치를 하나씩 맡아서 작업하다가, 결과물이 어느 정도 쌓이면 마스터 브랜치에 통합해서 다른 팀원과 공유하는 것이다.
   2. 독립 브랜치로 작업하는 기간이 길어질수록 작업 결과를 마스터로 통합하기가 어려워진다.
   3. 지속적 통합(CI), 트렁크 기반 개발(TBD)를 이용하여 기능별 통합 주기를 짧게 가져간다.
4. 테스팅
   1. 자가 테스트 코드는 리팩터링을 할 수 잇게 해줄 뿐만 아니라, 새 기능 추가도 훨씬 안전하게 진행할 수 있도록 도와준다.
   2. 또한 리팩터링 과정에서 버그가 생길 위험이 아주 크다는 불안감을 해소할 수 있다.
5. 레거시 코드
   1. 레거시 시스템을 파악할 때 리팩터링이 굉장히 도움된다.
   2. 대규모 레거시 시스템을 테스트 코드 없이 명로하게 리팩터링하기 어렵기 때문에 테스트 보강을 해야한다.
6. 데이터 베이스
   1. 데이터 베이스는 진화형 데이터베이스 설계와 데이터베이스 리팩터링 기법을 통해서 리팩터링을 할 수 있다.
   2. 변환을 수행하는 코드를 간단히 작성한 다음, 선언된 데이터 구조나 접근 루틴을 변경하는 코드와 함께 버전 관리 시스템에 저장한다.
   3. 데이터베이스 리팩터링은 프로덕션 환경에 여러 단계로 나눠서 릴리스하는 것이 대체로 좋다는 점에서 다른 리팩터링과 다르다.

## 6. 리팩터링, 아키텍처, 애그니(YAGNI)
향후 변경에 유연하게 대처할 수 있는 유연성 메커니즘을 소프트웨어에 심어 둔다. 다양한 예상 시나리오에 대응하기 위한 매개변수들을 추가한다.
하지만, 유연성 매커니즘이 오히려 변화에 대응하는 능력을 떨어트릴 때가 대부분이다.
리팩토링을 통해서 소프트웨어의 복잡도에 지장을 주지 않는 매커니즘은 마음껏 추가하지만, 복잡도를 높일 수 있는 유연성 메커니즘은 반드시 검증르 거친 후에 추가한다.
이런 식으로 설계하는 방식을 간결한 설계, 점진적 설계, YAGNI 등으로 부른다.

## 7. 리팩터링과 소프트웨어 개발 프로세스
최초의 애자일 소프트웨어 방법론 중 하나로 등장한 XP는 그 후 수년에 걸쳐 애자일의 부흥을 이끌었다.
자가 테스트 코드, 지속적 통합, 리팩터링을 적용한다면 YAGNI 설계 방식으로 개발을 진행할 수 있다.

## 8. 리팩터링과 성능
리팩터링하면 소프트웨어가 느려질 수도 있지만, 그와 동시에 성능을 튜닝하기에는 쉬워진다.

빠른 소프트웨어를 작성하는 방법 세 가지
1. 시간 예산 분배
2. 끊임없는 관심을 기울이기
3. 의도적으로 성능 최적화에 돌입하기 전까지는 성능에 신경 쓰지 않고 코드를 다루기 쉽게 만드는데 집중한다.

## 10. 리팩터링 자동화
리팩터링을 자동화하는 가장 어설픈 방법은 소스 코드의 텍스트를 직접 조작하는 것이다. 이 방식은 허점이 많기 때문에 테스트해보기 전에는 결과를 신뢰해서는 안 된다.
자동 리팩터링을 제대로 구현하려면 코드를 텍스트 상태가 아닌, 구문 트리로 해석해서 다뤄야 한다.
